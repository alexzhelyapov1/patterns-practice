### Шпаргалка: Factory Method

**Проблема**
Необходимость создавать объекты, точные типы и зависимости которых неизвестны на этапе написания базового кода.

**Решение**
Замена прямого вызова конструктора (`new`) виртуальным методом, который переопределяется в подклассах для генерации конкретных экземпляров.

**Плюсы / Минусы**
*   [+] **OCP:** Добавление новых продуктов не ломает существующий код создателей.
*   [+] **SRP:** Логика создания вынесена в одно место.
*   [+] **Loose Coupling:** Базовый код зависит от абстракций, а не от реализаций.
*   [-] **Class Explosion:** Требует создания параллельной иерархии классов (для каждого продукта нужен свой создатель).

**Code Snippet (C++20)**
```cpp
// Интерфейс продукта
struct IProduct {
    virtual ~IProduct() = default;
    virtual void execute() = 0;
};

// Базовый создатель
class Creator {
public:
    virtual ~Creator() = default;
    // Тот самый Factory Method
    [[nodiscard]] virtual std::unique_ptr<IProduct> create() const = 0;

    void businessLogic() const {
        if (auto prod = create()) prod->execute();
    }
};

// Конкретный создатель
struct ConcreteCreator final : Creator {
    [[nodiscard]] std::unique_ptr<IProduct> create() const override {
        return std::make_unique<ConcreteProduct>();
    }
};
```

**Когда НЕ использовать**
*   Если список создаваемых типов фиксирован и не будет расширяться (проще использовать `std::variant` или простой `switch`).
*   Если вам не нужна иерархия самих создателей (достаточно «Simple Factory» — статического метода).
*   В критических по производительности участках, где недопустим оверхед виртуальных вызовов (в таких случаях рассмотри паттерны на основе шаблонов/CRTP).
